## 2. 为什么根因只可能是「资格没生成 / 已过期」（v1 硬推理）

> **⚠ v2 已作废本节结论**：本节的硬推理成立于「第 2 道守卫极性正确」这一前提，而该前提是错的（见 §9.1）。`TryCounter` 实际在**任何正常状态下**都返回 `false`，所以"轻击能出"根本不能推出"资格没生成"。本节与 §3 只保留作为排查过程记录。

1. 你能打出**普通轻击** ⇒ 左键 `InputKey` 事件执行了 ⇒ 它第一颗调用 `TryCounter` 也执行了 ⇒ `TryCounter` **返回了 `false`**（返回 `true` 时会走 `CleanupCounter` 并播 3.25 秒的反击蒙太奇，不可能看不出来）。
2. `TryCounter` 的五个"状态门禁"里，四道在你的场景下**必然**为 `false`：
   - `bWeaponBusy` / `bIsDodging` / `bIsParrying` / `bIsHitStunned` / `bIsDead` —— `TryParry` 自己的门禁就是这同一批变量（`bWeaponInHand` + 五重 OR），你能成功按下招架，说明按招架时它们全是"可行动"值；
   - 招架成功后 `TryDefendAttack` 会先调 `CleanupParry`（复位 `bIsParrying`、`bParryWindowActive`），`TryParry` 开头会调 `CleanupDodge`（复位 `bIsDodging`）；
   - 招架成功时**你不再是受击方**（`DoAttackHit` 的 `Parried` 分支里 `ApplyDamageToTarget` 根本不走），所以 `bIsHitStunned` 不会被置起。
   - 这几个变量在招架成功后到按左键之间**没有任何写入点**能把它们变成 `true`（唯一的 `bWeaponBusy=true` 写入全在装备/卸下流程）。
3. 于是只剩两种可能：`bCounterReady == false`，或者 `CounterTarget` 无效。
   - `CounterTarget` 只在招架成功链里被赋成 `Attacker`（= `OwningNPC`，一个活着的 NPC Actor）；`EndCounterWindow` / `CleanupCounter` / 死亡清理才会清它。若它是空的，那说明资格链压根没走完，**归到同一种情形**。
4. 所以：**要么资格从来没生成（招架判定没成立），要么生成后过期了。**

## 3. 30 秒判别法（不用改任何蓝图）

> **状态（v2）**：已按本节执行过，结论见 §9 —— 三条招架打印**全部出现**（`BeParried` / `Defend: Parried` / `ParrySuccess: BP_MasterNpc`），即"情形 A 资格没生成"不成立；蓝色数字为 `0/1/2`（轻击连击序号），与 §9.1 的根因一致。本节保留为后续同类问题的判别步骤。

招架成功链上**已经有三条打印**，直接在 PIE 里看屏幕：

| 打印内容 | 出处 | 含义 |
|---|---|---|
| `Defend: Parried` | `TryDefendAttack/CallFunction_17` | 招架**判定**成立，进了成功链 |
| `ParrySuccess: <攻击者显示名>` | `TryDefendAttack/CallFunction_20` | 资格已生成（`bCounterReady=true`）且计时器已建 |
| `BeParried` | `AC_EnemyAttack/DoAttackHit/CallFunction_25` | 敌人侧确认被招架 |

**判别**：
- 三条都出现过 → **情形 B**（资格有了，按晚了），跳到 §3.2。
- 只有 `BeParried`，或一条都没有 → **情形 A**（判定没成立），跳到 §3.1。
- ⚠️ 注意区分"招架**动作**播了"和"招架**判定**成功"：前者只要 `bWeaponInHand` 为真、无冷却就能播，**与敌人是否在攻击你无关**；判定的失败路径是**静默**的（`Else → Return None`，零打印）。

### 3.1 情形 A：招架判定没成立（最可能）

判定式 = `bAttackParryable`（攻击可招架）**且** `bParryWindowActive`（你在 0.22 秒前按了招架键）**且** `dot(指向攻击者, 你的前向) >= cos(60°)`。

其中两项你可以手工确认，一项确认不了：

| 因子 | 现状 | 怎么查 |
|---|---|---|
| `bParryWindowActive` | `TryParry` 里 `SetTimerDelegate(EndParryWindow, combat.parry.window=0.22s)`，正确 | 按招架键的**时机**：必须在攻击落地**之前** 0.22 秒内按（不是"看到被打再按"） |
| 面向 | 正面 ±60°，代码正确 | 别背对敌人 |
| **`bAttackParryable`** | **全项目零写入点**（见 §4.3），只来自 `AC_EnemyAttack` 的 Class Default 勾选 | 打开 `AC_EnemyAttack` → 类默认值 → 搜 `Next Attack Parryable`，确认**已勾** |

**结论**：如果 `Defend: Parried` 没出现，第一步就去勾 `AC_EnemyAttack` 的 `bNextAttackParryable`（并列入 §5 的 F3 修复，把"手工勾选"变成真正的运行时逻辑）。

### 3.2 情形 B：资格有了但按晚了（次可能，但确实很容易踩）

实测时间线（全部有资产证据）：

| 时刻 | 事件 | 证据 |
|---|---|---|
| t = 0 | 你按下上侧键，`AM_Parry_L` 开始播，`bParryWindowActive=true`（0.22s） | `TryParry`：`Set bIsParrying=true` → `Set bParryWindowActive=true` → `PlayAnimMontage(AM_Parry_L)` → `SetTimerDelegate(EndParryWindow, 0.22)` |
| t ≈ 0.05–0.22 | 敌人攻击落地，判定成功 → **`bCounterReady=true`，1.5 秒资格窗口开始计时** | `TryDefendAttack` 成功链 |
| t = 0.417 | `ANS_InputDisabled` 结束（此前输入只影响"缓冲"，不拦反击） | `AM_Parry_L` 的 `Notifies(0)`，`Duration=0.417022` |
| **t = 1.0833** | **招架动作播完**（`AM_Parry_L.SegmentLength=1.083333`） | 蒙太奇资产 |
| t = 1.1 | `bIsParrying` 由 `EndParryAction` 复位（字面量 1.1s） | `TryParry` 的 `CreateDelegate_1` |
| **t ≈ 1.55–1.72** | **资格过期**（`EndCounterWindow` 清 `bCounterReady`） | 1.5s 窗口 |

⇒ **"等招架动作播完再按左键"，实际只剩约 0.5 秒**。这是设计口径（1.5s）与招架动作（1.08s）叠加出来的操作余量问题，不是接线错误。

**处置**：把 `combat.parry_counter.window` 从 `1.5` 调到 `2.0–2.5`（走数据管线，不要直接改 DataTable），或改成"招架动作结束才开始计资格窗口"。见 §5 的 F4。

## 4. 顺带查出的 5 个真实缺陷

### 4.1 【P0】反击蒙太奇没挂任何 Notify —— 反击即使触发也不掉血

`AM_Parry_Counter_Attack_L`（`Content/Combo_Demo/Animation/Montage/Parry/`）的 T3D 全文只有 15 行：有 `CompositeSections(0)=(Default, SegmentLength=3.25)`、有 `SlotAnimTracks`、有 `AnimNotifyTracks(0)=(TrackName="1")`，但**没有任何 `Notifies(...)` 行、也没有任何内嵌 Notify 对象 ⇒ Notify 数 = 0**。

对照同目录的 `AM_Parry_L`：`Notifies(0)=(NotifyName="ANS_InputDisabled_C", NotifyStateClass=..., Duration=0.417022)`；攻击类蒙太奇还多一条 `ANS_WeaponTrace_C`。

后果：
- 缺 `ANS_WeaponTrace` → 反击动作会播，但**不触发 `CallWeaponTrace(true)`、不结算伤害**（正好命中手册第 22 课"常见翻车③"）；
- 缺 `ANS_InputDisabled` → 反击期间不锁输入。

> 说明：`SlotAnimTracks` 在所有蒙太奇里都不写 `SlotName`（含能用的 `AM_Parry_L`），所以**不是槽位问题**，别往那边查。

### 4.2 第 22 课步骤 4 没实现：蒙太奇结束/中断 → `CleanupCounter`

`CleanupCounter` 全项目**只有一个调用点**：左键 `TryCounter==true` 分支。`TryParry` / `TryCounter` 用的是简单版 `PlayAnimMontage`（返回 float），**没有任何 `OnCompleted`/`OnBlendOut`/`OnInterrupted` 绑定**（`AC_Combat` 里 10 个 `AddDelegate` 全部来自 EventGraph 装备流程的「Play Montage (Callback Proxy)」）。

后果：反击播完/被打断后没有任何收尾（`CounterTarget` 可能残留、`bCounterReady` 依赖左键分支代偿）。目前靠"资格已被 `TryCounter` 自己消费掉"侥幸不炸，但**属未实现项**，且违反 AGENTS.md「每个状态必须写出置 true / 置 false 位置」。

### 4.3 `bNextAttackParryable` 全项目零写入（第 21 课 A14 欠账）

129 个缓存资产的 T3D 全扫，`bNextAttackParryable` 只在 `AC_EnemyAttack` 命中 5 次：1 次变量声明（`FriendlyName="Next Attack Parryable"`，说明"下次攻击能否被招架"）+ `DoAttackHit` 里 2 次读取 + 编译副本 2 次读取，**一次 `VariableSet` 都没有**。也就是说"哪一下能招架"完全由蓝图类默认值决定，永远不变 —— 与手册 v1.53 记载的"第 21 课 A14 未做、靠 Class Default 手工勾 true 临时验证"一致。这也是情形 A 的头号嫌疑。

### 4.4 `CombatGraph` 里有一颗游离的 `CleanupParry`

`CombatGraph/K2Node_CallFunction_18`（行 7021–7029）的 `execute` 与 `then` **都没有任何连线**，永远不会执行。建议删掉，避免以后误读成"左键分支还会清招架状态"。

### 4.5 `EndParryWindow` 的"成功后跳过冷却"判断恒为假

### 10.0 先定统一口径（这次出错的根源是"两套写法混用"）

本项目里"守卫分支"存在两种写法，混用就会接反：

| 写法 | 语义 | 谁在用 | 极性 |
|---|---|---|---|
| **A. 通行条件** | `条件成立` = 可以继续 | `TryParry/IfThenElse_0`（`bWeaponInHand`）、`TryDefendAttack/IfThenElse_0/1/3`、`LightAttack/IfThenElse_1`、`TryToDodge/IfThenElse_0`（`CanStartDodge`） | `then` → 继续；`else` → 失败/打印 |
| **B. 阻塞条件** | `条件成立` = 不能行动（一堆 OR） | `TryParry/IfThenElse_1`（已正确）、**`TryCounter/IfThenElse_1`（接反）** | `then` → `Return false`；`else` → 继续 |

**统一规则（写进手册，以后照此接线）**：
1. 守卫只用 **B 写法**：把"所有阻塞项"用一个 `OR` 拼在 `Condition` 上，**`then`（true）走失败出口、`else`（false）走继续**。理由：阻塞项是会持续增加的（死亡/硬直/闪避/招架/武器忙/下落……），B 写法加条件只需往 OR 上加一根线，不用动执行线。
2. `OR` 的 `Condition` 引脚默认值是 `true`，**没接线时等于"永远被挡"** —— 接完必须确认 `Condition` 上真的有一根线。
3. **不要**用 `NOT` 去翻一个 OR：`NOT(OR(...))` 与 B 写法语义相同，但排查时多一层，且和别的图不一致（本次修法 A 因此不作为首选）。
